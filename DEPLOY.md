# Развёртывание и обслуживание ПланТакт

Документ описывает три вещи: как выкатить приложение, как управлять схемой базы
через миграции и как настроить резервное копирование.

---

## 1. Схема базы данных: миграции

### Как это устроено

В режиме разработки (`NODE_ENV` не равен `production`) TypeORM сам приводит схему
к описанию сущностей — удобно, пока меняешь код. В production автосинхронизация
**отключена**: она способна молча удалить колонку вместе с данными. Там схему
меняют только миграции, и приложение применяет их само при старте.

Файлы миграций лежат в `backend/src/migrations` и попадают в сборку.

### Первая миграция (выполняется один раз)

Разработка ведётся на базе, где схема уже создана автосинхронизацией. Чтобы
зафиксировать её как исходную точку:

```bash
cd backend

# 1. Убедитесь, что .env указывает на вашу рабочую базу разработки
# 2. Сгенерируйте миграцию по текущим сущностям
npm run migration:generate

# Появится файл вида src/migrations/1737800000000-Migration.ts
```

Откройте файл и просмотрите его: там должны быть `CREATE TABLE` для всех таблиц.
Если в нём внезапно есть `DROP` чего-то нужного — не применяйте, разберитесь.

### Проверка на чистой базе

Прежде чем везти это в школу, убедитесь, что миграция разворачивает схему с нуля:

```bash
createdb plantakt_test
DATABASE_NAME=plantakt_test npm run migration:run
DATABASE_NAME=plantakt_test npm run migration:show   # все должны быть отмечены [X]
dropdb plantakt_test
```

### Повседневная работа

После изменения сущностей:

```bash
npm run migration:generate      # создать миграцию по разнице
npm run migration:run           # применить локально
npm run migration:show          # посмотреть статус
npm run migration:revert        # откатить последнюю
```

Миграции коммитятся в репозиторий вместе с кодом. Правило простое: изменение
сущности без миграции — незавершённая работа.

### Что происходит при деплое

При `NODE_ENV=production` приложение на старте применяет все непринятые миграции
самостоятельно. Отдельный шаг в скрипте деплоя не нужен, но **перед выкаткой
обязательно сделайте бэкап** (см. ниже).

## 2. Резервное копирование

### Что копируется

Копия состоит из двух частей, и обе одинаково важны:

- база данных — задачи, мероприятия, расписание, пользователи;
- папка `backend/uploads` — вложения к задачам и мероприятиям. Их нет в базе,
  и без этой папки файлы будут потеряны безвозвратно.

### Ручной запуск

```bash
bash scripts/backup.sh
```

Копии складываются в `backups/`:

```
plantakt_db_2026-07-25_0300.dump      — база
plantakt_files_2026-07-25_0300.tar.gz — вложения
```

Скрипт проверяет целостность дампа сразу после создания: если файл повреждён,
он удаляется и скрипт завершается с ошибкой — вы узнаете о проблеме сейчас,
а не в момент восстановления.

Копии старше 14 дней удаляются автоматически. Изменить: `KEEP_DAYS=30 bash scripts/backup.sh`.

### Автоматический запуск (Linux, cron)

```bash
crontab -e
```

Добавьте строку — копия каждую ночь в 3:00:

```
0 3 * * * cd /путь/к/school-task-manager && bash scripts/backup.sh >> /var/log/plantakt-backup.log 2>&1
```

Проверьте через сутки, что файлы появились и лог без ошибок.

### Куда складывать копии

Каталог задаётся переменной `BACKUP_DIR`. **Держать копии на том же диске, что и
базу, — плохая идея**: отказ диска уносит и данные, и копии. Минимум — другой
диск, лучше — другой сервер или объектное хранилище:

```
0 3 * * * cd /путь/к/school-task-manager && BACKUP_DIR=/mnt/backup/plantakt bash scripts/backup.sh
```

### Восстановление

```bash
bash scripts/restore.sh                                        # список копий
bash scripts/restore.sh backups/plantakt_db_2026-07-25_0300.dump
```

Скрипт запросит подтверждение (нужно ввести «да»), затем сделает страховочную
копию текущего состояния и только потом перезапишет базу. Вложения
восстанавливаются автоматически, если рядом лежит архив с той же меткой времени.

### Проверка восстановления

Бэкап, который ни разу не восстанавливали, бэкапом не является. Раз в квартал:

```bash
createdb plantakt_check
DATABASE_NAME=plantakt_check bash scripts/restore.sh backups/<последняя копия>.dump
# запустите приложение на этой базе и убедитесь, что данные на месте
dropdb plantakt_check
```

## 3. Порядок выкатки новой версии

```bash
# 1. Бэкап — всегда первым шагом
bash scripts/backup.sh

# 2. Забрать код
git pull

# 3. Бэкенд
cd backend
npm ci
npm run build

# 4. Фронтенд
cd ../frontend
npm ci
npm run build

# 5. Перезапустить бэкенд (миграции применятся автоматически)
```

Если после обновления что-то сломалось — откатывайте код и восстанавливайте базу
из копии, сделанной на первом шаге.

---

## 4. Переменные окружения

Файл `backend/.env` (в репозиторий не попадает):

```
NODE_ENV=production
DATABASE_HOST=localhost
DATABASE_PORT=5432
DATABASE_USER=plantakt
DATABASE_PASSWORD=<пароль>
DATABASE_NAME=plantakt
PORT=3000
FRONTEND_URL=https://ваш-домен
```

`NODE_ENV=production` — ключевая строка: именно она отключает автосинхронизацию
схемы и включает применение миграций.
